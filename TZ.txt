ТЗ: локальный TIPA FAQ Pipeline

1. ЦЕЛЬ ПРОЕКТА

Нужно создать локальный Node.js/TypeScript pipeline для автоматической обработки текстовых расшифровок видео проекта TIPA HOUSE.

Исходные данные — текстовые файлы расшифровок .txt.

Pipeline должен:
1. находить новые расшифровки в папке transcripts/;
2. отправлять текст на анализ AI;
3. извлекать из текста вопросы и ответы;
4. нормализовать вопросы;
5. определять разделы и теги;
6. объединять одинаковые или близкие вопросы из разных видео;
7. сохранять источники;
8. обновлять единую базу FAQ в data/faq.json;
9. запоминать уже обработанные файлы;
10. работать локально, кроме обращения к AI API;
11. пока НЕ использовать Firebase.

2. СТРУКТУРА ПРОЕКТА

tipa-faq/
├── transcripts/
│   └── *.txt
├── data/

│   ├── sections.json
│   ├── tags.json
│   └── processed.json
├── src/
│   ├── index.ts
│   ├── process.ts
│   ├── ai.ts
│   ├── merge.ts
│   └── types.ts
├── prompts/

├── .env
├── .gitignore
├── package.json
├── tsconfig.json
└── README.md

Если проект уже существует, сначала проанализируй его структуру и адаптируй решение, а не создавай дублирующиеся файлы.

3. ФОРМАТ FAQ

data/faq.json:

{
  "version": 1,
  "updatedAt": null,
  "items": []
}

Каждый FAQ item:

{
  "id": "faq-001",
  "sourceQuestions": [
    {
      "text": "А вот зимой-то вообще реально строить?",
      "source": "video-017.txt",
      "context": "..."
    }
  ],
  "question": "Можно ли строить дом зимой?",
  "answer": "Да, строительство возможно зимой при соблюдении необходимых условий...",
  "sections": [
    "construction",
    "materials"
  ],
  "tags": [
    "газобетон",
    "зима",
    "строительство"
  ],
  "sources": [
    "video-017.txt"
  ]
}

4. ИСХОДНЫЙ ВОПРОС ОБЯЗАТЕЛЬНО СОХРАНЯТЬ

Не удалять и не заменять исходную формулировку вопроса.

AI должен создавать два уровня:

sourceQuestions — реальная формулировка из расшифровки.

question — нормализованный пользовательский вопрос.

Пример:

Исходный:
"А вот зимой-то вообще реально строить? Ну, то есть если уже морозы начинаются?"

Нормализованный:
"Можно ли строить дом зимой?"

5. НЕСКОЛЬКО ИСТОЧНИКОВ

Если разные видео содержат один и тот же вопрос, НЕ создавать несколько FAQ.

Например:
"Можно ли строить дом зимой?"
"Можно ли заниматься строительством в зимний период?"
"Реально ли строить дом зимой?"

должны рассматриваться как потенциально один FAQ.

Все исходные формулировки сохранять в sourceQuestions, а все файлы — в sources.

6. ДОПОЛНЕНИЕ СУЩЕСТВУЮЩЕГО ОТВЕТА

Если новый файл содержит дополнительную информацию по уже существующему FAQ, НЕ создавать новый FAQ.

Нужно дополнить существующий ответ, не теряя информацию из предыдущих источников.

Если новый источник противоречит существующему ответу, не принимать решение автоматически. Пометить такой случай для ручной проверки.

Например, при необходимости:

"conflicts": [
  {
    "source": "video-025.txt",
    "description": "Новый источник содержит утверждение, отличающееся от предыдущего ответа."
  }
]

7. SECTIONS

Разделы FAQ — независимая сущность.

data/sections.json:

{
  "version": 1,
  "sections": [
    {
      "id": "construction",
      "title": "Строительство"
    },
    {
      "id": "materials",
      "title": "Материалы"
    },
    {
      "id": "insulation",
      "title": "Утепление"
    },
    {
      "id": "project",
      "title": "Проектирование"
    },
    {
      "id": "technology",
      "title": "Технологии"
    },
    {
      "id": "cost",
      "title": "Стоимость"
    },
    {
      "id": "terms",
      "title": "Сроки"
    }
  ]
}

FAQ может относиться сразу к нескольким разделам:

"sections": [
  "materials",
  "insulation",
  "construction"
]

Не хранить название раздела непосредственно в FAQ. FAQ должен хранить только ID разделов.

Это позволит в будущем менять структуру разделов без переработки FAQ.

8. TAGS

Теги — отдельная система и НЕ должны смешиваться с sections.

Sections используются для навигации по сайту.
Tags используются для поиска, фильтрации, группировки и внутреннего анализа.

data/tags.json:

{
  "version": 1,
  "tags": [
    "газобетон",
    "d400",
    "утепление",
    "стены",
    "зима",
    "проект",
    "сроки"
  ]
}

AI должен использовать существующие теги, если они подходят.

Новые теги не добавлять автоматически без необходимости. Если нужен новый тег, сообщить о нём отдельно.

9. ОБРАБОТКА ФАЙЛОВ

Все расшифровки находятся в:

transcripts/

Обрабатывать только *.txt.

Создать data/processed.json:

{
  "version": 1,
  "files": {}
}

Для каждого обработанного файла хранить:
- имя файла;
- hash содержимого;
- дату обработки.

Если файл не изменился — повторно его не обрабатывать.
Если файл изменился — обработать снова.

10. AI EXTRACTION

Создать src/ai.ts.

AI получает текст расшифровки и возвращает строго структурированные данные.

Для каждого найденного вопроса:
- sourceQuestion;
- normalizedQuestion;
- answer;
- sections;
- tags.

AI НЕ должен:
- придумывать факты;
- добавлять информацию, которой нет в исходном тексте;
- превращать рекламные заявления в проверенные факты;
- делать категоричные выводы при наличии оговорок;
- удалять важные ограничения или условия.

Если ответ в расшифровке отсутствует, это должно быть отражено явно.

11. НОРМАЛИЗАЦИЯ ВОПРОСА

AI преобразует разговорную формулировку в понятный пользовательский вопрос.

Например:

"А если мы зимой будем это всё делать, нормально вообще?"

→

"Можно ли выполнять строительство зимой?"

Смысл исходного вопроса изменять нельзя.

12. MERGE

Создать src/merge.ts.

Перед созданием нового FAQ проверять существующие FAQ.

Проверять не только точное совпадение строк, но и семантическое соответствие.

Если уверенность недостаточна — НЕ объединять автоматически. Такие случаи выводить как кандидатов на ручную проверку.

13. BACKUP

Перед изменением data/faq.json создавать backup.

Например:

data/backups/faq-2026-10-08T120000.json

Не удалять предыдущие backup автоматически.

14. DRY-RUN

Добавить:

npm run process:dry

Команда должна:
- прочитать новые файлы;
- выполнить AI extraction;
- определить новые/изменённые FAQ;
- показать предполагаемые изменения;
- НЕ изменять faq.json, processed.json и tags.json.

Обычная команда:

npm run process

должна применить изменения.

15. ОСНОВНАЯ КОМАНДА

npm run process

Алгоритм:

1. Найти *.txt в transcripts/
2. Проверить processed.json
3. Найти новые/изменённые файлы
4. Прочитать текст
5. Отправить текст AI
6. Получить структурированные FAQ
7. Проверить sections
8. Проверить tags
9. Сравнить вопросы с существующими FAQ
10. Объединить совпадающие
11. Создать новые FAQ
12. Создать backup
13. Сохранить faq.json
14. Обновить processed.json
15. Вывести итоговый отчёт

16. КОНФИГУРАЦИЯ AI

Использовать .env:

OPENAI_API_KEY=
OPENAI_BASE_URL=
OPENAI_MODEL=

Не помещать API key в исходный код.

Архитектура должна позволять использовать:
- OpenAI-compatible API;
- OpenRouter;
- локальный Ollama;
- другой совместимый endpoint.

Для Ollama должна поддерживаться конфигурация:

OPENAI_BASE_URL=http://localhost:11434/v1
OPENAI_MODEL=qwen3.5:4b

API key для Ollama не должен быть обязательным.

17. TYPESCRIPT

Использовать строгую типизацию.

Создать src/types.ts с типами для:
- FAQ;
- SourceQuestion;
- Section;
- Tag;
- ProcessedFile;
- AI extraction result.

Не использовать any без необходимости.

18. ЛОГИРОВАНИЕ

При запуске npm run process выводить понятный отчёт:

TIPA FAQ processor

Found files: 12
New files: 2

Skipped: 9

AI extraction:

Merge:

Result:

Ошибки должны быть понятными и содержать имя файла.

19. БЕЗОПАСНОСТЬ

Не хранить API keys, секреты и пароли в Git.

Добавить необходимые файлы в .gitignore.

20. README

Создать README.md с инструкцией:
1. установка зависимостей;
2. создание .env;
3. запуск Ollama;
4. установка/выбор модели;
5. добавление .txt файлов;
6. dry-run;
7. обычная обработка;
8. структура JSON;
9. подключение другого AI provider.

21. НЕ ДЕЛАТЬ НА ПЕРВОМ ЭТАПЕ

НЕ делать:
- Firebase;
- веб-интерфейс;
- авторизацию;
- базу данных;
- frontend;
- автоматический watcher;
- Docker;
- deployment.

Нужен простой локальный CLI pipeline.

22. ПОРЯДОК РАБОТЫ CLINE

Сейчас работа выполняется в режиме PLAN.

Сначала:
1. Проанализируй существующий проект.
2. Проверь, какие файлы уже существуют.
3. Определи, что можно переиспользовать.
4. Предложи архитектуру.
5. Укажи потенциальные проблемы.
6. Особое внимание удели merge одинаковых вопросов и структуре JSON.
7. НЕ изменяй файлы.

После согласования плана будет выполнен переход в ACT для реализации.

Не создавай файлы и не выполняй команды изменения проекта, пока не будет дано отдельное разрешение перейти к ACT.
